# Store privacy forms: Amplitude analytics update (27 September 2026)

Internal working notes. Not published: `release-tools/` is excluded from the Pages build (`release-tools/build_site.py`, `ignored` set).

What changed: Amplitude Analytics now records app interaction events (screens opened, features used, feature success/failure), tied to the account's internal user id (Supabase auth UUID) plus a random per-install id. No ads, no cross-app tracking, no selling. In-app opt-out: Settings -> Share usage analytics (default on). Amplitude Experiment (remote feature flags) receives the internal user id and a random per-install device id (a UUID generated by the app, not a hardware or advertising id).

Public policy: https://www.aastroastra.com/privacy.html#analytics (section "Analytics and feature settings").

### Can this be applied by API instead? (explained, not called)
Yes, in principle. The Android Publisher API v3 has `applications.dataSafety`:

```
POST https://androidpublisher.googleapis.com/androidpublisher/v3/applications/com.avdstudiox.android/dataSafety
Body: { "safetyLabels": "<entire CSV file contents as one string>" }
```

What is needed:
1. The CSV. Get it from the Console: App content -> Data safety -> **Export to CSV** (downloads the current answers in Google's question/response format). Edit it to add the App interactions rows (collected = true, ephemeral = false, optional, purposes App functionality + Analytics) and the extra Device or other IDs purpose, keeping Google's question IDs exactly. Google also publishes a blank template in the Console import dialog. The API only accepts this CSV format, not JSON.
2. Credentials: the existing service account used for Play releases, with a Console permission that can manage policy declarations / app content for this app (release-only permissions are not enough; if the call returns 403, grant it in Users and permissions).
3. It is not part of an edit (`edits.insert`/`commit` are not used). It replaces the whole Data safety form in one go, so a mistake in the CSV overwrites correct answers. Always start from a fresh export.
4. It still needs to be sent for review from Publishing overview, like a Console change.

For a single added row, the Console is quicker and safer. The API is worth it if these answers will change often.

## B. App Store Connect: App Privacy

Path: App Store Connect -> Apps -> AastroAstra -> (sidebar) **App Privacy** -> Data Types -> **Edit**.

No public API: the App Store Connect API does not expose App Privacy ("nutrition label") answers, so this is a manual step. It must be done before the next **App Store** submission. TestFlight builds do not need it.

Is data collected from this app? **Yes, we collect data from this app.**

Tick these data types, then Save. After saving, each ticked type shows "Set up <type>" to answer purpose, linking and tracking.

| Category | Data type | Purposes to tick | Linked to the user? | Used for tracking? |
|---|---|---|---|---|
| Contact Info | Name | App Functionality | Yes | No |
| Contact Info | Email Address | App Functionality | Yes | No |
| Contact Info | Phone Number | App Functionality | Yes | No |
| User Content | Other User Content (birth date, time, place) | App Functionality | Yes | No |

| Identifiers | **User ID** (new or re-check) | App Functionality, **Analytics** | Yes | No |
| Identifiers | **Device ID** (new) | App Functionality, **Analytics** | Yes | No |
| Usage Data | **Product Interaction** (new) | App Functionality, **Analytics** | Yes | No |
| Diagnostics | Crash Data / Performance Data (if already declared) | App Functionality | per existing answer | No |

Notes on the answers:
- Device ID: the flag client and analytics send a random per-install UUID (`experiment_device_id` in UserDefaults on iOS), and the device session registrar keeps a device id. Apple counts any device-level identifier, so declare it. It is linked because it is sent together with the user id.
- Tracking = No for all: nothing is combined with third-party data for advertising, no data broker sharing, no IDFA. The app must not show the App Tracking Transparency prompt for this.
- In the Apple form "Analytics" means our own product analytics, which is correct here. Do not tick Third-Party Advertising, Developer's Advertising or Marketing, or Product Personalization.
- Birth details: Apple has no "birth details" type; "Other User Content" is the usual fit. If the existing label already declares these under a different type, keep the existing choice for consistency.

After all types are set up: click **Publish** at the top of the App Privacy page. Privacy Policy URL (App Information page): `https://www.aastroastra.com/privacy.html`.

## Open points to confirm (not guessed)
- **Retention 12 months**: the policy now says we keep analytics for up to 12 months. Set the matching data retention in Amplitude (Organization settings -> Data retention) or change the policy text to the real value. Amplitude's default is to keep data for the life of the contract, so without a setting the policy would be untrue.
- **Approximate country**: Amplitude derives location from the request IP and by default stores city and region too, plus the IP. The policy says "approximate country". To match, turn off IP / city / region / DMA tracking in the Amplitude project settings. Otherwise widen the policy wording.
- **Device model**: the Android analytics code on `feature/chat-assistant-polish` sends platform, OS version and app version but not device model; the Amplitude Experiment SDK does send device model and manufacturer. The policy mentions device model, which is accurate overall.
- **Share usage analytics toggle**: not found in the Android or iOS checkouts I inspected (probably on another branch). Confirm it ships before the policy goes live, and that turning it off stops `api2.amplitude.com` event calls while flags still load.
- **Account deletion**: the policy promises analytics are deleted or unlinked on account deletion. That needs a step in the deletion runbook: call Amplitude's User Privacy API (deletion request by user_id) when an account is deleted.
- **DPDP**: the existing privacy page has no explicit DPDP Act section (no Data Fiduciary, Grievance Officer or consent-manager wording), so there was nothing to keep consistent with. The new section describes consent withdrawal (the toggle) and the cross-border transfer in plain language only. A proper DPDP notice (grievance officer contact, Board complaint right, legal basis) should be reviewed by counsel.
- **Other processors not named on the policy**: OneSignal (push notifications) and RevenueCat (purchases) are in the apps but not in the "Who processes your data" list. Not changed here; worth adding.
- **iOS privacy manifest**: the app target has no PrivacyInfo.xcprivacy of its own (only the SDKs' manifests). The app uses UserDefaults (a required-reason API) and now collects Product Interaction / User ID / Device ID; Apple expects the app's own manifest to declare these. Check before the next App Store upload.

## C. Firebase / Google Ads measurement (added 27 Sep 2026, ships with Android 229 / iOS 216)

What changes: Google Analytics for Firebase is added only to measure our own Google Ads campaigns. Events: first_open (automatic), sign_up (method), kundali_generated (first), purchase (pack, INR value), plus Firebase's automatic session/app-update events. User ID = internal account ID. Android reads the advertising ID (AD_ID permission) for ad attribution; iOS uses FirebaseAnalyticsWithoutAdIdSupport (no IDFA, no ATT prompt) + SKAdNetwork. Ad personalisation signals are off. The in-app "Share usage analytics" switch turns Firebase off too.

### Google Play Data safety (edit the same form as section A)
- Device or other IDs: keep ticked. Purposes add **Advertising or marketing** (ad attribution) next to App functionality and Analytics. Collected: yes. Shared: **No** (Google acts as our service provider for Firebase/Google Ads measurement; per Google's Firebase data-disclosure guidance this is "collected", not "shared"). Required: yes.
- App activity > App interactions: purposes add **Advertising or marketing**. Optional (user can switch off).
- Financial info > Purchase history (already declared): purposes add **Analytics** and **Advertising or marketing** (purchase value is sent for campaign measurement).
- Also in App content: **Advertising ID** declaration: answer **Yes, the app uses an advertising ID**, purpose **Analytics** and **Advertising or marketing** (measurement only). This is a separate App content item, must match the AD_ID permission in the manifest.
- Save, then Publishing overview > Send changes for review (together with Android 229).

### App Store Connect > App Privacy (iOS)
- Add or confirm: **Purchase History** (Analytics, App Functionality; linked; not tracking), **Product Interaction** (Analytics; linked; not tracking), **User ID** (Analytics, App Functionality; linked; not tracking), **Device ID**: NOT collected by Firebase on iOS (no IDFA); keep whatever Amplitude's random install ID required (Analytics; linked; not tracking).
- "Used to track you": **No** for everything (no IDFA, no ATT).
- Needed before the next App Store submission (not TestFlight).
